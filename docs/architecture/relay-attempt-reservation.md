# Local Planner attempt reservation

`FileAttemptReservation` implements `TrustedAttemptReservation` for a trusted caller-supplied, pre-existing absolute directory. It does not install a host adapter or authorize dispatch. The caller must retain the directory for the life of all attempts and must not place it in a synchronized, shared, or ephemeral location.

The filename is a SHA-256 digest of a JSON array in fixed field order: canonical host, canonical repository, issue number, run ID, task ID, attempt ID. `requirementsVersion` and policy settings remain excluded. The version 2 record contains those identity fields, digest, policy digest, approved source commit, and approved requirements version; it contains no approved issue body, credentials, provider payload, or approval evidence. Hashed filenames are opaque, but the record's identity is readable to the owning user.

The provider requires a private directory owned by the current user, rejects symlinks and unsafe ancestors, and accepts only recognized local APFS, ext4, XFS, or Btrfs filesystem types. It does not create the directory. Exclusive creation (`O_EXCL`) selects one claimant across local processes. The winner writes the record, syncs the file, closes it, syncs the parent directory, and checks the directory again before returning `RESERVED`. A second claimant reads the existing file without following symlinks. Only an exact, regular, private, single-link version 2 record with the same policy binding yields `ALREADY_RESERVED`; a legacy, partial, corrupt, mismatched, or unreadable record throws. Neither result authorizes another dispatch. All uncertain writes, syncs, and closes throw, and the record is retained for manual reconciliation.

This design assumes the caller controls the directory and that no same-user adversary changes ancestors or files concurrently. Node path-based operations cannot pin every ancestor against malicious same-user replacement. Filesystem type detection is conservative and does not prove mount options, storage hardware, or remote backing. Local process concurrency and process restart are covered by exclusive creation and retained files. A crash before creation leaves no claim; a crash after creation leaves either an incomplete hold or a duplicate claim. Tests exercise local-process behavior and injected ambiguous I/O. File and directory synchronization provide the available OS durability barrier, but physical power-loss durability remains unproven. A human must reconcile ambiguous records; there is no release, expiry, deletion, overwrite, or automatic retry path.

The existing Planner handoff still requires exact model, reasoning-effort, and fresh-context proof. Current host compatibility remains unproven, so this provider is not a live-dispatch readiness decision.

## Immutable policy coordination

`policy-coordination.ts` derives policy identity from a full Git commit in a trusted checkout. Git must resolve that exact commit, and its committed policy bytes must match the checkout file. The strict parser requires schema version 1, all three named roles, and nonempty model and effort tokens. It freezes the settings read from that commit; there is no second hard-coded model table or fallback setting. The handoff still compares supplied settings exactly with the authoritative repository policy. The version 1 digest encoding is a JSON array of encoding version, policy schema version, then ordered `[role, model, reasoningEffort]` tuples, hashed with SHA-256. Approval evidence is an explicit trusted caller input; the module cannot independently prove the human approval event.

The reservation directory contains `.active-policy.json`, which records the canonical GitHub host and repository, active digest, source commit, and promotion approval evidence. The canonical identity is derived from the checkout's HTTPS GitHub origin. Promotion is a separate explicit operation. It takes the same exclusive `.policy-gate.json` used by attempt dispatch, rejects an active reference for another repository and any legacy, corrupt, or incomplete claim, and replaces the active reference only after verifying completion evidence for every retained version 2 reservation. An attempt's trusted host and repository must match the checkout origin and active reference. A successful Planner response alone cannot authorize promotion. The operational script is never run against a real repository as part of verification.

An attempt acquires the local gate before reserving and keeps it through capability checks and the host dispatch call. The active reference, checkout policy bytes, and gate identity are rechecked before each capability check, after each await, immediately before dispatch, and after dispatch. The host receives a frozen request containing the policy digest, source commit, and exact Planner settings. A policy or identity mismatch, ambiguous reservation, ambiguous dispatch, malformed response, or crash leaves the gate and permanent claim held for explicit reconciliation. There is no gate lease, timeout, stale-gate reclaim, claim release, or automatic retry.

Clean outcomes write an exclusive completion sidecar, sync it and the directory, then verify and remove the transient gate and sync the directory again. A clean pre-reservation stop removes only the gate. The permanent reservation is never deleted, including after a validated Planner response or a verified no-dispatch outcome. An incomplete completion or gate cleanup is uncertain and requires reconciliation. A missing completion sidecar blocks promotion even if no gate is visible. The completion sidecar records a digest and `NO_DISPATCH` or `VALIDATED_RESPONSE`; it does not claim downstream work was approved.

This coordinates processes sharing one trusted local directory. It assumes the directory is retained, private, and not modified by a same-user adversary. The Git checkout and approval evidence are trusted caller boundaries; the module cannot establish host-executed model/effort or fresh-context proof. A filesystem gate is not a distributed lock. Mount options, storage hardware, and physical power-loss behavior remain unproven. No production `PlannerHost` adapter or live agent dispatch is provided.
